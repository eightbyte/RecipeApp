# Phase 9.3 — Corpus-Derived Ingredient Catalogue

**Version:** 1.1
**Date:** 2026-09-12
**Status:** Accepted — open questions answered (§11), implemented; artefact built, awaiting review (§12.3)
**Depends on:** Phase 9 Stage 4 complete (1,123 normalised recipes are the evidence base *and* the input)
**Supersedes:** Phase 9 §12.1 (*Ingredient catalogue growth*) and its "run `seed-catalogue` before `seed-recipes`" instruction
**Retires:** `IngredientCatalogueSeeder` as an LLM generator, and the `seed-catalogue` command name; `import-catalogue` takes over the job from a committed artefact
**Blocks:** Phase 9 Stage 5 — this changes how Stage 5 resolves ingredients, so it lands first

> **Why this is its own spec and not an edit to Phase 9.** Phase 9 §12.1 assumed the catalogue was
> an input to the import and that the import would grow it. The finished Stage 4 corpus inverts
> that: the recipes are now the best available evidence for what the catalogue should contain, and
> deriving it from them turns Stage 5's most expensive and least deterministic step into a
> dictionary lookup. That is a design change to a stage not yet built, plus one EF migration on a
> v1-feature-complete app — the same class of change as Phase 9.1, and it should be reviewable on
> the same terms.

---

## 1. The proposal under review

> the original process was to generate a base ingredient list generated by the LLM. However, now
> that we have all these recipes normalized we have a great collection of data we can extract I
> would imagine. Would it be beneficial to change the seed-process to instead import these
> ingredients as a distinct list out of the recipes, use that as a basis to create another
> normalized set of ingredients we can normalize, categorize into grocery store categories using an
> LLM, and then have a data set that can be checked in for easy seeding in the future?

**Verdict: yes, and the case is stronger than "better data".** The generated catalogue is not merely
less accurate than a corpus-derived one — it is *unrelated* to the corpus, and the current Stage 5
design compensates for that at runtime in a way that is order-dependent, expensive and unreviewable.
§2 measures the gap; §3 sets out the runtime defect that only this change removes.

Two things in the proposal need sharpening, and §5 does it:

- **"normalize" is doing two different jobs.** Folding `onions` into `onion` is mechanical and
  safe. Folding `diced tomatoes` into `tomatoes` is *wrong* — every one of the 32 corpus lines
  reads `1 can (14.5 ounces) … diced tomatoes` — and no mechanical rule distinguishes the two
  cases. The merge decision is a judgement, which is the half that earns an LLM and a committed
  review surface.
- **The LLM should not be asked for everything.** Category genuinely needs it (§2.4). Default unit
  does not — the corpus states it 8,882 times (§2.5). Density must *never* be asked for; that
  stance is already settled and documented in [IngredientDensitySeeder](../backend/RecipeApp.API/Data/IngredientDensitySeeder.cs).

## 2. Measured evidence

All figures below are measured against the 1,123 files in `seed-data/myplate/normalised/`, the
completed Stage 4 artefact, using the ingredient `name` exactly as Stage 4 wrote it.

### 2.1 What the corpus actually holds

| | Result |
|---|---:|
| Recipes | 1,123 |
| Ingredient rows | 8,882 |
| Distinct normalised names | **1,475** |
| Names appearing exactly once | 827 (56.1%) |

Frequency is steeply concentrated, which matters for how much of the result a human can realistically review:

| Threshold | Distinct names | Share of all rows |
|---|---:|---:|
| ≥ 2 occurrences | 648 | 90.7% |
| ≥ 3 occurrences | 444 | 86.1% |
| ≥ 5 occurrences | 290 | 80.3% |
| ≥ 10 occurrences | 174 | **71.9%** |

**174 names carry 72% of the library.** A reviewer who reads only those has checked most of what a
user will ever see in a shopping list.

### 2.2 What the generated catalogue covers

The hand-written starter list in [DataSeeder.cs](../backend/RecipeApp.API/Data/DataSeeder.cs) is 41 names.

| | Result |
|---|---:|
| Its names that occur in the corpus at all | 35 / 41 |
| Corpus rows it matches exactly | 2,037 / 8,882 (**22.9%**) |
| Its names absent from the corpus entirely | **6** |

The six absentees are the finding, not the 22.9%: `capsicum`, `plain flour`, `beef stock`,
`coconut milk`, `salmon fillet`, `cream`. **Three of those are British/Australian spellings of
things the corpus names in American English** — the corpus says `bell pepper` (34 rows) and
`green pepper` (56), `all-purpose flour` (39), `beef broth` (5). Seeded as they stand, they do not
match, do not consolidate in a shopping list, and sit permanently beside their American twin.

`seed-catalogue`'s LLM output is not measured here because it is not reproducible — it generates
from the model's notion of "common household cooking ingredients", with a rolling exclusion list of
up to 200 previously produced names ([IngredientCatalogueSeeder.cs:69](../backend/RecipeApp.API/Services/IngredientCatalogueSeeder.cs#L69)).
Its relationship to this corpus is coincidental by construction. That is the point.

### 2.3 The duplication, and which half of it is mechanical

| Folding rule | Families | Names absorbed | Rows involved |
|---|---:|---:|---:|
| Singular ↔ plural only | 86 | 86 | 2,234 |
| Modifier-stripped form is itself a corpus name | 170 | 278 | 816 |
| **Both combined** | — | **366** | — |

Mechanical folding alone takes **1,475 → 1,109** distinct names. Representative families:

```
[tomato]   tomatoes(66) tomato(63) diced tomatoes(32) crushed tomatoes(5)
           low-sodium diced tomatoes(5) low-sodium tomatoes(5) whole tomatoes(3) canned tomatoes(2)
[yogurt]   yogurt(81) plain yogurt(6) fat-free plain yogurt(4) low-fat plain yogurt(4)
           plain low-fat yogurt(3) low-fat yogurt(2) non-fat yogurt(2) non-fat plain yogurt(1)
[milk]     milk(104) skim milk(13) fat-free milk(10) low-fat milk(6) non-fat milk(6) whole milk(2)
[spinach]  spinach(16) frozen spinach(9) fresh spinach(8) frozen chopped spinach(4) canned spinach(1)
```

**And this is exactly why the mechanical pass must not be allowed to decide.** Of the four families
above, `[yogurt]` and `[milk]` should collapse and `[tomato]` and `[spinach]` must not:

| Name | Every corpus source line reads | Verdict |
|---|---|---|
| `diced tomatoes` | `1 can (14.5 ounces) no salt added diced tomatoes` | **canned** — a different aisle from `2 medium tomatoes` |
| `frozen spinach` | `1 package (10 ounce) frozen spinach, thawed` | **frozen** — a different aisle from `6 cups fresh spinach` |
| `skim milk` | `1/3 cup skim milk` | same purchase as `1/2 cup milk, non-fat` |

The `milk` row is the tell: **the corpus already records the fat variant in two different places** —
sometimes in the name (`skim milk`), sometimes in the notes (`milk` + `non-fat`). Merging makes the
library self-consistent; it does not discard anything, because `RecipeIngredient.SourceText` and
`Notes` keep the line verbatim (Phase 8.5.1 §6.2).

### 2.4 Categorisation is the part that genuinely needs the LLM

`RecipeScrapeService.CategoriseIngredient` is a first-keyword-wins table
([RecipeScrapeService.cs:647](../backend/RecipeApp.API/Services/RecipeScrapeService.cs#L647)). Run over all 1,475 names:

| Category | Distinct names | Rows |
|---|---:|---:|
| PRODUCE | 372 | 3,049 |
| **OTHER** | **341** | **1,366 (15.4%)** |
| CONDIMENTS | 159 | 1,256 |
| DRY_GOODS | 158 | 1,249 |
| DAIRY | 157 | 937 |
| MEAT_SEAFOOD | 126 | 394 |
| BEVERAGES | 47 | 258 |
| CANNED | 41 | 173 |
| BAKERY | 52 | 146 |
| FROZEN | 22 | 54 |

The 15.4% falling to `OTHER` includes `water`(242), `margarine`(57), `chili powder`(56),
`cilantro`(36), `cabbage`(22), `green beans`(20), `cauliflower`(11) — ordinary supermarket items.

**The misclassifications are worse than the gaps**, because first-keyword-wins is confident:

| Name | Rows | Keyword verdict | Because |
|---|---:|---|---|
| `peanut butter` | 27 | DAIRY | `butter` |
| `chicken broth` | 37 | MEAT_SEAFOOD | `chicken` precedes `broth` |
| `cream of mushroom soup` | 5 | DAIRY | `cream` |
| `egg noodles` | 5 | DAIRY | `egg` |
| `tomato juice` | 9 | BEVERAGES | `juice` |
| `egg substitute` | 3 | DAIRY | `egg` |

A shopping list that files peanut butter under Dairy looks correct and sends the user to the wrong
aisle. `OTHER` at least signals "unknown". This is the strongest argument in the proposal: **one
careful LLM pass over 1,475 names, reviewed once and committed, replaces a keyword table that is
wrong on items appearing in hundreds of recipes.**

### 2.5 Default unit does not need the LLM — the corpus states it

Unit distribution across all 8,882 rows: `cup` 3,052 · `pcs` 1,849 · `tsp` 1,773 · `tbsp` 1,187 ·
`g` 674 · *(none)* 331 · `ml` 16.

Of the 444 names with ≥ 3 rows:

| Modal-unit share | Names |
|---|---:|
| ≥ 80% one unit | **258** |
| 50–80% | 162 |
| < 50% — genuinely mixed | **17** |
| never quantified at all | 7 |

`onion` is 176 `pcs` / 131 `cup` / 42 `tbsp` — modal `pcs`, which is how you buy one. `salt` is 317
`tsp` / 30 unquantified / 9 `pcs` — modal `tsp`. **The modal unit over a merged group is a measured
answer, and `DefaultUnit` is only a suggestion in the UI anyway.** Asking a model for it would
replace 8,882 observations with a guess.

73 names never carry a unit in any recipe (Phase 9.1's population — `salt and pepper`,
`nonstick cooking spray`). Those get a null `DefaultUnit`, which the column already allows.

### 2.6 Density coverage — mostly *not* a gap to fill

| | Result |
|---|---:|
| Curated density rows / name aliases | 50 / 124 |
| Corpus rows measured in `cup` | 3,052 |
| …covered by an existing density alias | 558 (**18.3%**) |
| Distinct names measured in cups | 710, of which 48 have a density |

The uncovered 2,494 rows read alarmingly, and mostly should not be fixed. The largest are `water`
(220), `milk` (89), `orange juice` (34), `chicken broth` (34), `vegetable oil` (30), `mayonnaise`
(24), `vinegar` (16) — liquids sold by volume — and `onion` (131), `celery` (64), `carrots` (33),
`broccoli` (30), `cilantro` (20) — packing-dominated. **`GramsPerMillilitre == null` is the correct
outcome for both** (CLAUDE.md, Phase 8.5.1 §5.3).

What this phase owes the density seeder is narrower and concrete: **its 124 aliases are matched
against catalogue names, and this phase changes the catalogue names.** §4.6 handles it.

### 2.7 Two defects in the Stage 4 output that only a catalogue pass will catch

Stage 4's gate checks quantities. It never reads `displayName`, and it cannot:

- **126 names carry more than one `displayName`; 206 rows disagree with their own modal form.**
  Mostly harmless casing (`Vegetable oil`, `black pepper`) and stray specificity (`Onon`,
  `Small Onion`, `Extra Virgin Olive Oil` for `olive oil`).
- **13 rows across 4 recipes have `displayName: "Diced Tomatoes"` on an ingredient that is not a
  tomato.** `dirty-rice` has it on **all ten** of its rows — `water`, `ground beef`, `onion`,
  `cooked rice`, `black pepper`. This is the Stage 4 worked example leaking into the answer. It is
  invisible to the gate because every quantity on those rows is correct.
  - A rerun of `dirty-rice` corrected most entries.  Manual review and revision fixed `dried egg mix` normalized as `Diced Tomatoes`.

A corpus-derived catalogue fixes both structurally: `DisplayName` is chosen once per canonical
entry and every recipe row renders through it.

## 3. Why Stage 5 as specified cannot deliver this

Phase 9 §12 routes Stage 5 through `RecipeScrapeService.NormaliseAsync` and `ConfirmAsync`. Three
consequences, all of which this phase removes:

**3.1 The matching prompt grows as the run proceeds, and the result depends on manifest order.**
[NormaliseAsync](../backend/RecipeApp.API/Services/RecipeScrapeService.cs#L435) reloads the whole
catalogue per recipe and sends **every** entry as a match candidate:

```csharp
var candidateList = candidates.Select(c => $"{c.idx}: {c.ing.DisplayName} ({c.ing.Category})")
```

At 1,475 entries that list is 47,063 characters — **≈ 11,800 tokens per recipe**, on top of the
recipe itself, 1,123 times. Worse, unmatched rows become new catalogue entries during the run
([ConfirmAsync → ResolveOrCreateIngredientAsync](../backend/RecipeApp.API/Services/RecipeScrapeService.cs#L194)),
so recipe #1 is matched against ~200 candidates and recipe #900 against ~1,300. **The same
ingredient name can resolve differently depending on where its recipe sits in the manifest**, and
re-running the import on another machine can produce a different catalogue. That is the opposite of
what Phase 9 §18 Q1 committed `normalised/` to achieve.

**3.2 Every runtime-created catalogue row is born bare.** `ResolveOrCreateIngredientAsync` sets
`Name`, `DisplayName`, `Category` and nothing else — **no `DefaultUnit`, no `GramsPerMillilitre`**.
So an import that creates ~1,400 rows guarantees that none of them can ever resolve a cup, and
`seed-densities` afterwards only helps the handful whose invented name happens to hit one of the
124 aliases.

**3.3 1,123 LLM matching calls are unreviewable.** Nobody can audit a thousand in-flight
confidence scores. 1,109 committed rows can be read in an afternoon, and corrected with an edit
rather than a re-run.

## 4. Design

### 4.1 Shape

A new **Stage 4.5**, between normalise and persist, with two halves that run at different times:

```
normalised/*.json ──►  --build-catalogue  ──►  seed-data/ingredient-catalogue.json   [authoring: GPU, once, committed]
                                                          │
import-catalogue ◄──────────────────────────────────────────┘                          [seeding: no GPU, idempotent]
     │
     ├──► seed-densities        (unchanged, now alias-aware)
     └──► seed-recipes --persist  (Stage 5: deterministic lookup, zero LLM calls)
```

The authoring half runs **once, by whoever has the GPU**, and its output is reviewed and committed.
Every other machine — CI, a new developer, a rebuild — runs only the seeding half. This is the same
bargain Phase 9 §18 Q1 struck for `normalised/`, for the same reason.

### 4.2 The artefact

`backend/RecipeApp.API/seed-data/ingredient-catalogue.json` — **committed**. It sits outside
`seed-data/myplate/`, so `--refresh-cache` cannot touch it and the existing `.gitignore` rules
(which ignore `seed-data/**/raw/`, `parsed/`, `normalised/`, `images/`, `state.json`) already leave
it tracked without a new exception.

```jsonc
{
  "version": 1,
  "generatedAt": "2026-09-12T…Z",
  "source": {
    "corpus": "myplate",
    "recipes": 1123,
    "ingredientRows": 8882,
    "distinctNames": 1475
  },
  "entries": [
    {
      "name": "chickpeas",                  // normalised, lowercase — Ingredient.Name
      "displayName": "Chickpeas",           // Ingredient.DisplayName
      "category": "CANNED",                 // IngredientCategory.All
      "defaultUnit": "g",                   // MeasurementUnit.All, or null
      "aliases": ["garbanzo beans", "canned chickpeas", "chick peas"],
      "corpusRows": 22,                     // provenance: how much evidence backs this entry
      "corpusRecipes": 19
    }
  ]
}
```

Deliberately **not** in the artefact:

- **`gramsPerMillilitre`.** [IngredientDensitySeeder](../backend/RecipeApp.API/Data/IngredientDensitySeeder.cs)
  is the single source of truth for density — curated, cited, human-reviewed, and explicitly not
  LLM-generated. Two sources would be one too many.
- **Anything recipe-specific.** The catalogue says what an ingredient *is*, never how much of it a
  recipe uses.

Ordering is by `name` ascending so a regenerated file diffs cleanly against the committed one.

### 4.3 Building it — `seed-recipes --build-catalogue`

Four passes. The first and third are deterministic; only the second uses the model.

**Pass 1 — collect (deterministic).** Walk `normalised/*.json`, accumulating per distinct `name`:
occurrence count, distinct recipe count, unit histogram, `displayName` histogram, and **up to three
representative `sourceText` lines**. No LLM, no database. Fails loudly if `normalised/` is
incomplete or any file's `parsedFingerprint` is stale — the catalogue must describe the corpus that
will actually be persisted.

**Pass 2 — group and categorise (LLM, batched by head noun).** Names are batched **by their final
word** so that every member of a family is judged in the same call. `tomato`, `tomatoes`,
`diced tomatoes`, `crushed tomatoes` and `low-sodium tomatoes` arrive together; arbitrary batching
splits them across calls and *guarantees* an inconsistent answer. Batches are capped (~40 names) and
a family larger than the cap is split by frequency, most-frequent first.

Each name is presented with its corpus frequency **and its representative source lines**. The source
lines are not decoration — §2.3 showed `diced tomatoes` is only identifiable as canned from its
line, and the name `cranberries` covers both `2 cups fresh or frozen cranberries` and
`1 cup dried cranberries`, which are different purchases. The name alone is not sufficient evidence.

The model returns, per group: canonical `name`, `display_name`, `category`, and the member names it
absorbs. It is **not** asked for `default_unit` — §4.4.

> **The model is never shown a proposed grouping.** Phase 9 §23.3 measured what happens when this
> prompt family is handed a menu: given the ten fraction conversions it needed, the model stopped
> reading the source line and started choosing from the list, and the error class got nearly three
> times worse. The mechanical folding of §2.3 is therefore used **only to route names into batches**
> — never to suggest an answer. A test asserts the prompt contains no pre-computed grouping.

**Pass 3 — derive units and pick display names (deterministic).** For each confirmed group:

- `defaultUnit` = the modal unit over the **merged** group's rows, or `null` if the group has no
  quantified row (§2.5). Canonicalised through `MeasurementUnit.TryCanonicalise` before storing.
- `displayName` = the modal `displayName` over the group's rows, title-cased, **except** where the
  model supplied one for the canonical name — the model wins there, because §2.7 showed the modal
  value is sometimes a leaked example.

**Pass 4 — validate and write (deterministic).** §4.7. Written atomically through the existing
`SeedCacheStore` write helper so a crashed run cannot leave a half-file.

Cost: 1,475 names in ~40 batched calls. At Stage 4's measured ~9 s per call this is **under 15
minutes**, against Stage 4's ~3 hours. It is cheap because it runs once per corpus, not once per
recipe.

### 4.4 What the LLM is and is not asked

| Field | Source | Why |
|---|---|---|
| Grouping / aliases | **LLM** | A judgement no mechanical rule gets right (§2.3) |
| `category` | **LLM** | The keyword table is wrong on common items (§2.4) |
| `displayName` | **LLM**, corpus modal as fallback | Fixes the leaked-example defect (§2.7) |
| `defaultUnit` | **Corpus modal** | Stated 8,882 times; a guess would be worse (§2.5) |
| `corpusRows` / `corpusRecipes` | **Corpus count** | Provenance |
| `gramsPerMillilitre` | **Never** — curated seeder owns it | Settled in Phase 8.5.1 (§2.6) |

### 4.5 Seeding it — `import-catalogue`

> **Resolved (§11 Q2): `seed-catalogue` is renamed to `import-catalogue`.** The old token is still
> recognised, and answered with an error naming the replacement rather than ignored — silently
> starting the web host instead would look like the command had run. The rename covers *every* form,
> not just `seed-catalogue <count>`: the count argument is gone because the catalogue's size is a
> property of the corpus, not a number anyone picks.

`import-catalogue` **keeps the job — populate the ingredient catalogue — and changes its source from
an LLM to the committed artefact.** It is: no LLM, no network, no arguments, idempotent, and fast
enough to run at Development startup beside `seed-densities`.

- Insert an entry whose `Name` is absent.
- If `Name` is present, fill only the nulls (`DefaultUnit`, `Category` where it is the `"OTHER"`
  default, missing aliases). **Never overwrite a value a human has corrected** — the same contract
  `IngredientDensitySeeder` already honours.
- `--force` re-applies the artefact over existing rows, for a deliberate refresh.

`IngredientCatalogueSeeder.cs` and `IngredientCatalogueSeederTests.cs` are deleted. The `count`
argument goes with them; `seed-catalogue` in any form is an error naming `import-catalogue`.

**Order matters and the command enforces it**: catalogue → densities → recipes. `seed-densities`
cannot attach a density to a row that does not exist, and Stage 5 cannot resolve a cup without one.

### 4.6 `Ingredient.Aliases` — one column, one migration

```csharp
/// <summary>
/// Alternate names that resolve to this catalogue entry — regional spellings ("capsicum" for
/// "bell pepper"), plurals, and corpus variants the Phase 9.3 pass folded in. Used by the
/// exact-match lookup so a known synonym never reaches the LLM matching pass.
/// Every alias is normalised lowercase, and no alias may equal any entry's Name (§4.7).
/// </summary>
public string[] Aliases { get; set; } = [];
```

Mapped by Npgsql to `text[]`. Migration: `AddIngredientAliases`. **No index**: every consumer
already loads the full catalogue into memory —
[NormaliseAsync](../backend/RecipeApp.API/Services/RecipeScrapeService.cs#L435) projects all rows on
each call — so the lookup is a dictionary build, not a query. At ~1,100 rows that is the right
trade.

The lookup dictionary is keyed by `Name` **and** every alias:

```csharp
var exactLookup = new Dictionary<string, Guid>(StringComparer.OrdinalIgnoreCase);
foreach (var i in dbIngredients)
{
    exactLookup[i.Name] = i.Id;
    foreach (var alias in i.Aliases) exactLookup.TryAdd(alias, i.Id);   // Name always wins
}
```

**This benefits ordinary scraping too, not just seeding** — which is why the column exists rather
than the aliases living only in the JSON. A user scraping a recipe that says `garbanzo beans` now
gets an exact hit on pass 1 instead of an LLM call on pass 2. Pass 2 is unchanged and still handles
genuinely novel names.

`IngredientDensitySeeder` gains the same alias awareness: its 124 `CatalogueNames` are matched
against `Name` **or** `Aliases`, which is what keeps §2.6 working after the catalogue names change.

### 4.7 Validation — enforced at build time and again at seed time

A catalogue that contradicts itself is worse than no catalogue, so both halves check:

1. Every `name` is unique, lowercase, non-blank.
2. Every `category` satisfies `IngredientCategory.IsValid`.
3. Every non-null `defaultUnit` satisfies `MeasurementUnit.IsValid` (strict — canonicalise first).
4. **No alias appears on two entries**, and **no alias equals any entry's `name`.** This is the one
   that silently corrupts a lookup, and it cannot be expressed as a Postgres constraint at
   reasonable cost — so it is a code invariant with a test.
5. **Every one of the 1,475 corpus names is reachable** as either a `name` or an `alias`. A name the
   pass dropped is a recipe that cannot be persisted, and §4.8 would fail it at import; catching it
   here names the problem at authoring time instead.
6. `corpusRows` sums to 8,882.

### 4.8 Stage 5 becomes a lookup

`seed-recipes --persist` no longer calls `RecipeScrapeService.NormaliseAsync`. A new
`Services/Seeding/SeedCatalogueResolver` maps a `NormalisedSeedRecipe` to a `ScrapeConfirmRequest`:

- Resolve each row's `name` through the alias-aware dictionary → `IngredientId`. **Zero LLM calls.**
- Apply the existing measurement stages — `MeasurementConverter.ToCanonical` then
  `ResolveForImport` against the matched entry's density — by calling the same helpers
  `NormaliseAsync` uses. These are extracted, not duplicated.
- **A miss fails that one recipe**, logged with the slug and the unresolved name, and the run
  continues — the per-slug failure isolation Stages 3 and 4 already use. A miss means the committed
  catalogue is stale relative to `normalised/`, which is a real error and should be loud.
  `--allow-unknown-ingredients` falls back to create-on-the-fly for anyone who wants the old
  behaviour.

**`ConfirmAsync` remains the single persistence path**, so Phase 9 §12's "no parallel persistence
logic" holds. Only preview *construction* changes, and only for seeding.

### 4.9 `DataSeeder` reconciliation

`DataSeeder` keeps its role — two sample recipes so a fresh install is not empty — but stops being a
second source of catalogue truth. Its 41-name block is removed. Its two recipes resolve their
ingredients through the same alias-aware lookup after `import-catalogue` has run, and insert a row
only if nothing matches.

This is what fixes §2.2's real problem: `capsicum` resolves to `bell pepper`, `plain flour` to
`all-purpose flour`, `beef stock` to `beef broth` — as **aliases**, so both spellings keep working
and only one row exists. The build pass is seeded with these three plus the other regional pairs a
reviewer adds; they are corpus-absent by definition, so §4.7 rule 5 will not surface them.

## 5. The merge rules

The rules the pass-2 prompt states, and which a reviewer checks the artefact against. Each is
derived from a measured corpus case, not from taste.

**Merge:**

| Rule | Evidence |
|---|---|
| Singular ↔ plural | 86 families, 2,234 rows (§2.3) |
| Fat / sodium / sugar variants | `milk` records `non-fat` in the *notes* on some lines and in the *name* on others (§2.3). Merging makes the library consistent; `SourceText` keeps the line. |
| Cut and size descriptors | `medium onion`, `diced onion` — you buy an onion |
| Regional spelling | `capsicum` → `bell pepper` (§4.9) |
| Redundant qualifiers | `fresh cilantro` → `cilantro` (fresh is the default form) |

**Do not merge:**

| Rule | Evidence |
|---|---|
| Preservation state changes the aisle | `diced tomatoes` is canned in all 32 lines; `frozen spinach` is frozen in all 9; `dried cranberries` ≠ `cranberries` |
| Cooked ≠ raw where both are bought | `cooked rice` is kept distinct — but see §7 |
| Different species or cultivar | `green onion` ≠ `onion`, `sweet potato` ≠ `potato` |
| A branded or compound product | `cream of chicken soup` ≠ `chicken broth` |

**The tie-break, when a rule is arguable: do not merge.** An over-split catalogue shows two lines in
a shopping list, which a user can see and understand. An over-merged one silently sums a can of
tomatoes into a punnet of fresh ones, which they cannot.

   survives in `SourceText` and `Notes` and is visible on the recipe; a shopping list that says
   "3 cups milk" is more useful than three lines. Worth a second opinion before the artefact is
   committed, because it is expensive to reverse afterwards.

     sodium and sugar variants, and `SourceText`/`Notes` keep every line verbatim.

2. **Is `seed-catalogue` the right name for a command that no longer generates anything?** It still
   seeds the catalogue, so the name is honest, and keeping it avoids breaking anyone's habits. The

   the name**, with the behaviour change called out in `CLAUDE.md`.

## 12. Implementation record — what the build changed about this spec

Five things were settled by writing the code and running the corpus rather than by reading §4.

- **`DataSeeder`'s entry guard had to move from ingredients to recipes, and §4.9 did not say so.**
  It opened `if (await db.Ingredients.AnyAsync()) return;`, which was a sound "already seeded" test
  while it was the only seeder. §4.5's mandated catalogue → densities → recipes order makes it
  always true, so the two sample recipes would have silently stopped appearing. Covered by
  `DataSeederTests.StillSeedsWhenTheCatalogueHasAlreadyBeenLoaded`.

- **§4.7's six rules cannot all run in both places.** Rules 5 (every corpus name reachable) and 6
  (`corpusRows` sums to 8,882) need the corpus, which the seeder does not have. Split into
  `IngredientCatalogueValidator.Validate` (rules 1–4, run at build *and* seed time) and
  `ValidateAgainstCorpus` (rules 5–6, build only).

- **The grouping pass needed a retry, which §4.3 did not give it.** Measured on the first real run:
  one batch of nine names returned `{"groups": []}` — valid JSON, no exception — and those nine
  names were silently demoted to the keyword categoriser this phase exists to stop relying on.
  Placing every label is the prompt's central instruction, so failing to do so is detectable and
  worth another call. The builder now retries a batch that leaves names unplaced, up to
  `MaxLlmRetries`, and reports what it could not place.

- **The canonical-name choice cannot be made inside a batch — so the model no longer makes it.**
  A name the model proposes may be another *batch's* corpus name, and accepting it would make one
  string both an entry's name and another entry's alias — §4.7 rule 4's exact subject. It first
  moved to the pass that sees the whole corpus as a vetted suggestion; with the §12.1 redesign the
  model is not asked for a name at all. An entry is named after its **most-used member**, ties going
  to the shorter name (`onion` before `onions`, `milk` before `skim milk`), derived exactly the way
  `defaultUnit` is. §4.3's "the model returns, per group: canonical `name`" and §4.4's table are
  superseded on this point. A consequence worth knowing: `beets` can name an entry whose alias is
  `beet`, so regional spellings now find their target by name **or** alias — by name alone,
  `beetroot` would have been skipped silently.

- **`ResolveOrCreateIngredientAsync` is alias-aware too, which §4.6 scoped to pass 1 only.**
  Without it, confirming a hand-typed `garbanzo beans` inserts a row whose `Name` equals an alias of
  `chickpeas` — and since the lookup loads names before aliases, that row then permanently shadows
  the alias. Ordinary use must not be able to break the invariant the artefact is validated against.

### 12.1 Pass 2 — how the grouping pass was made trustworthy

**Status (2026-09-12): the artefact is built and awaiting human review; it is not committed.**
`seed-recipes --build-catalogue` wrote `seed-data/ingredient-catalogue.json` — **1,190 entries from
1,475 names, all six §4.7 validations passing, 52 model calls.** §10 step 3's review is the remaining
step, and §12.3 lists what it should look at first.

Six full or partial corpus runs and three benchmark previews:

| Run | Change | Result |
|---|---|---|
| 1 | §4.3 as specified — one object per *group* | One batch returned `{"groups": []}` — valid JSON, no exception. Nine names silently demoted to the keyword categoriser. **No retry existed.** |
| 2 | + coverage gate and retry | 212 names → 64 groups (30% retention). One batch put **all 39 of its names in a single group**. |
| 3 | + anti-merge framing and a worked example | ~40% retention; the cereals batch still collapsed 17 names to 2. |
| 4–5 | **one object per *name*** with `same_as`, union-find, plural-folded batching, merge logging | 737 entries (50%) — refused by the 800 floor, but **every other §4.7 rule passed.** Heterogeneous batches were fixed (batch 4: 1 group → 29); the tomato batch collapsed 36 names, toothpicks included, into one. |
| preview | + prompt rules for "a particular kind" and "a choice", category enum, tolerant echo, collapse guard | On the benchmark: names wrongly merged **119 → 57** of 245. |
| preview | + §5 merge vocabulary refinement (offline, against runs 5 and the preview) | **0 of 245** wrongly merged. |
| **6** | **all of the above, full corpus** | **1,190 entries (80.7%), 0 of 245 benchmark names wrongly merged, 55 of 120 must-merge pairs missed.** Written. |

**1. The task was the wrong shape.** Asking for a **partition** of 40 names is one global,
combinatorial judgement. Inspecting the real batches disproved the first theory — that head-noun
batching makes a batch *look* homogeneous — because batch 4 spans beef, beets, berries, bouillon and
bread and the model merged them anyway. Pass 2 now asks the way Phase 9 §23 proved: one object per
labelled name — `label`, `name`, `same_as`, `display_name`, `category`, in that decode order — and
groups are the connected components of `same_as`. Copying `name` back puts the name being judged
directly in front of the decision, and doubles as the drift check Stage 4 lacked. The canonical name
is no longer asked for at all (§12's bullet above).

**2. Batching was splitting singular from plural.** Keyed on the raw final word, `tomato` and
`tomatoes` are different families, and greedy packing put a batch boundary between them in **8
families** (`tomato`, `mushroom`, `bean`, `pea` among them) — making §2.3's best-evidenced merge rule
one the model could never apply. §4.3 had specified the opposite. Family keys now fold a plural onto a
singular **the corpus itself uses** (68 folds, none wrong; `molasses` and `hummus` have nothing to fold
into), and only `pepper` spans batches, because it is larger than the cap.

**3. A count cannot review a catalogue.** Batch 1 is 37 names that honestly form about 20 purchases,
so "37 → 14" alone could not say whether the model was wrong. The builder now logs every merge and
every refusal. A hand-labelled benchmark of **8 batches, 245 names** — each pair must-merge,
must-not, or arguable per §5 — scored every change after run 5. It is deliberately failure-weighted:
six of its batches were chosen *because* they failed, so it measures the failure shapes, not the
corpus-wide rate.

**4. Every error was an over-merge, and prompt wording stopped paying.** Across the benchmark the
per-name model missed **1** must-merge pair while wrongly merging **119** names. The shape was
always the same — a general name absorbing particular kinds that share its final word: `egg noodles ←
lasagna | fettuccine | ramen`, `mustard ← dijon | spicy brown`, `flour ← whole wheat | rye | cake`,
fourteen cereals into `cereal`, `bacon` into `turkey bacon`, `green beans ← frozen green beans`. A
rule naming that exact shape, plus a worked example teaching it, halved the count to 57 — and left
noodles, mustard and cereals untouched.

**5. §5's MERGE list became a closed vocabulary that refines, and never proposes.**
`CatalogueMergeVocabulary` holds exactly §5's merge list: plural forms, fat/sodium/sugar variants, size
and cut words, redundant freshness qualifiers, three spellings (`filet`, `chile`, `purée`) and two
context rewrites (`whole milk`, `head of`). A merge the model proposed stands only where the names
differ by nothing else; the rest of the group is split in the over-split direction §5's tie-break
already chose. **It cannot create a merge the model did not make**, so the judgement §2.3 says no
mechanical rule can make — `diced tomatoes` is canned — stays the model's, and §4.3's "mechanical
folding only routes" still holds. Measured: 0 of 245 wrongly merged, at the cost of about half the
must-merge pairs. **This is the decision in this record most worth a second opinion**, because the
vocabulary is where precision was bought: words were left out *because* each would admit a real false
merge seen in the logs — `ground` (`ginger ← ground ginger`), `dried` (`cranberries ← dried
cranberries`), `white` (`beans ← white beans`), `cooked` (§5 keeps cooked and raw apart). The price
is visible: `ground cinnamon` is its own entry beside `cinnamon`.

**6. Degenerate answers are detected structurally.** In run 5, **263 of 264** merges spanned three
families or fewer, every two-family span a spelling (`chile`/`chili`, `fillet`/`filet`,
`leaves`/`leaf`). The one above was the tomato collapse, spanning five. A group spanning more than
`CatalogueMaxFamiliesPerGroup` (3) now marks the attempt defective, so the batch is retried; one still
collapsed after every attempt is dissolved. Run 6 needed no dissolving.

**7. Smaller things found only by running it.**
- **`category` is an enum.** As a free string, the model answered `SPICES` and `CONDIMENT` despite
  "MUST be exactly one value from this list". `JsonSchemaGrammar` gained `enum` support; run 6 had
  zero invalid categories. The prompt also states that spices and dried herbs are `CONDIMENTS`, which
  is the keyword table's existing convention, not a new one.
- **The name echo tolerates asides.** Stage 4 left `paprika (optional)` in the corpus and the model
  copies it as `paprika`; an exact check called that drift and spent two retries on a correct answer.
  An echo that is exactly *another* label's name is still refused.
- **The worked example is a family the corpus lacks** (plums), rendered by the same code as a real
  batch and run through the real reader in a test. The first example used the tomato family, which
  handed the tomato batch its answer.
- **`--build-catalogue --batch <n>`** runs pass 2 on named batches and writes nothing — `--slug`'s
  counterpart. A full build is ~45 minutes; the benchmark preview is ~10.

**8. §8's expected range was right; the floor stays.** §8 predicted 1,000–1,150 from mechanical
folding's 1,109. Run 6 lands at 1,190, slightly above, because the vocabulary errs towards splitting.
The 800 floor caught run 5's 737 exactly as intended.
